## 一、项目定位

### 1.1 一句话定位

> **一个为中文用户从零打造、Windows 优先、永久免费开源的图像编辑器 —— 平替 Photoshop。**

### 1.2 我们解决什么

| 痛点 | 现状 | 我们的答案 |
|------|------|-----------|
| **贵** | Photoshop 订阅制，年费上千 | **永久免费 + 开源（MIT）**，绝不做收费 / 会员 / 广告 |
| **不顺手** | GIMP 交互逻辑和 PS 差太远，用惯了 PS 的人迁移成本高 | **PS 级交互与快捷键**，肌肉记忆直接迁移 |
| **不在 Windows / 没有中文** | Compositor 只支持 macOS 26 + Apple 芯片，且**完全没有汉化** | **Windows 原生优先 + 中文原生**（不是汉化包，是天生中文） |
| **工具割裂** | 修图、导出、批处理散在多个软件 | **一体化**：从打开到导出，一个窗口闭环 |

### 1.3 明确不做的事（边界）

- ❌ 不做在线版 / 云端协作（先做单机桌面，**图片不出本机**）
- ❌ 不做 3D、视频剪辑、动画时间轴（另一个品类）
- ❌ 不追求「像素级复刻 PS 的每一个菜单」（要的是**工作流等价**，不是功能清单堆砌）
- ❌ **不 fork、不套壳、不抄 Compositor 的代码**（参考设计与逻辑，实现全部自研）
- ❌ **不做任何商业化**（无付费墙、无会员、无广告、无数据上报）

## 二、为什么做（背景）

1. **Compositor 给了信心，也留了空位。** 它证明了「一个人 + 开源 + AI 辅助」也能做出 PS 级的东西（7.7k star，MIT 协议，图层 / 蒙版 / 调整图层 / Camera Raw / PSD 读写一应俱全）。但硬伤是：**只跑 macOS 26 + Apple 芯片，且一个中文字符都没有**。
2. **Windows + 中文 = 巨大的空白。** 国内绝大多数设计 / 电商 / 自媒体用户是 Windows，中文界面是刚需；现有方案要么是昂贵的 PS，要么是半汉化 / 老版本。
3. **移植不可行，但重写可行。** 已实测：把 Compositor 移植到 Windows **不可行**——它是 SwiftUI + AppKit + Metal + Vision 全家桶（217 个 Swift 文件、4.5 万行），这些框架在 Windows 上没有对应物，**本质是重写而非移植**。既然都要重写，那就**从零写一个更干净的**。
4. **低依赖是可达的。** Compositor 的 `Package.resolved` 里**只有一个第三方库**（Sparkle，自动更新），其余全是系统框架与 9 个自研 C 内核——证明「自包含、少依赖」完全做得到，我们照这个标准来。
5. **技术条件成熟。** Web 图形栈（WebGPU / WebGL2 / WASM / Worker）已能撑起专业级图像编辑；Electron 能把 Web 技术干净地打包成 Windows 桌面应用。可控、可维护、跨平台潜力大。

## 四、参考项目 Compositor 拆解

> `D:\Compositor`（commit `11d8d7a`，v1.4.5）**完整保留**，作为功能 / UI / 逻辑的参考蓝本。以下为拆解结论。

### 4.1 依赖：干净到只有一个第三方库

| 项 | 内容 |
|----|------|
| 第三方依赖 | **仅 Sparkle 2.10.0**（macOS 自动更新框架），见 `Package.resolved` |

### 4.2 UI 布局（46 个 UI 文件 → 结构地图）

| 分区 | 文件 | 布局启示 |

> **不借鉴**：Swift / SwiftUI 的具体实现与 Mac 专属 API（在 Windows 上无从复用）。

### 4.3 逻辑骨架：9 个自研 C 内核

| 内核 | 职责 | 我们对应的自研模块 |
|------|------|------------------|
| `AdjustPixels.c` | 色调 / 明暗调整 | 调整层 shader |
| `LevelsPixels.c` | 色阶 | 色阶 / 曲线 shader |
| `BrushPixels.c` | 画笔落笔 | 画笔引擎（GPU） |
| `HealPixels.c` | 修复画笔 | 修复 / 污点工具 |
| `ContentFill.c` | 内容识别填充 | 内容识别填充（WASM / GPU） |
| `LensPixels.c` | 镜头校正 | 镜头校正滤镜 |
| `NoisePixels.c` | 噪点 | 添加杂色 |
| `DitherPixels.c` | 抖动 | 降色 / 导出抖动 |
| `WandPixels.c` | 魔棒选区 | 魔棒 / 按色选区 |

> **借鉴**：把**重计算拆成独立、可测试、语言无关的内核**这一架构——我们的对应物是 **WASM / WebGPU compute 模块**，同样独立、可单测。

### 4.4 工程格式：`.comp` 的设计（值得照抄思路）

`Compositor` 的 `.comp` = 一个**文件夹**，内为 `manifest.json` + `images/<图层UUID>.png`。

**设计精髓（我们要全盘继承）：**

- **非破坏**：图层像素与变换**分开存**，变换不烧进像素，随时可改；
- **明文可读**：manifest 是 JSON，**脚本 / AI 能直接生成与修改**；
- **显式校验 + 版本演进**：schema 已迭代到 **v11**，每一版都明确「旧版读不了就拒绝」，绝不误渲染；有像素上限（单边 3 万 px、合计 1 亿 px、1 万图层）等硬性防护；
- **原子保存**：协调式原子替换，避免半保存损坏。

> **我们的对应**：沿用**同一思路**（文件夹 + manifest + PNG 图层，扩展名随命名定），并在 v1 就引入**显式校验 + 版本号 + 往返测试**。

### 4.5 一句话总结

> **参考它的「骨」（功能划分、UI 骨架、格式设计、逻辑架构），自研它的「肉」（每一行实现）。**

## 五、底层框架映射（macOS → Windows → 我们实际用什么）

> 这是回应「底层要做清晰、库要找到 Windows 对应」的核心章节。三层对照：**Compositor 用什么 → Windows 原生对应什么 → 我们实际采用什么**。

### 5.1 图形与图像

| 能力 | Compositor（macOS） | Windows 原生对应 | 我们实际采用 | 许可 |

## 六、技术架构

### 6.1 选型总览

| 层 | 选型 | 理由 |
|----|------|------|
| **桌面外壳** | **Electron** | 打包 Windows `.exe` 最直接；桌面快捷方式 / 文件关联 / 自动更新都有成熟方案 |
| **界面** | **TypeScript + React + Vite** | 复杂面板组件化省心；热更新开发体验好 |
| **渲染引擎** | **WebGPU 优先，WebGL2 回退** | 图层合成、混合模式、调整、滤镜走 **GPU shader**，这是达到 PS 级流畅度的关键 |
| **矢量 / 文字** | **Skia（canvaskit-wasm）** | 复杂路径与排版有工业级实现可用 |
| **重计算** | **WASM SIMD + Web Worker + SharedArrayBuffer** | 内容识别填充、抠图、PSD/RAW 解析、色彩转换丢 Worker，主线程不卡 |
| **AI 推理** | **ONNX Runtime（DirectML EP）** | 选择主体 / 去背景 / 生成式填充，**本地跑、不上传** |
| **状态** | **Zustand + Immer** | 文档 / 工具 / 历史栈可预测，撤销重做友好 |

### 6.2 渲染管线（核心中的核心）

```
文档模型（图层树 + 蒙版 + 调整 + 样式 + 变换矩阵）
        │
        ▼
   分块瓦片（Tile）缓存 ── 脏矩形失效，只重画变化的块
        │
        ▼
   GPU 合成（WebGPU）
   ├─ 逐层：变换 → 混合模式（PS 全套）→ 不透明度 → 蒙版 → 剪贴
   ├─ 调整层 / 图层样式：WGSL compute / shader 实时求解
   └─ 视口：缩放 / 平移 / 像素网格
        │
        ▼
     画布显示  ←→  导出 / 保存（离屏按全分辨率重渲染）
```

**关键设计决策：**

- **非破坏优先**：变换存矩阵、调整存参数、文字存文本，**尽量不提前栅格化**（沿用 Compositor `.comp` 的思路）。
- **分块 + 脏矩形**：大文档只重算变化区域。
- **CPU / GPU 各司其职**：能上 GPU 的绝不走 CPU；必须 CPU 的进 Worker。
- **精度**：内部按 **16 位/通道** 设计（P2 起），避免多次调整后的色阶断层。

### 6.3 关键子系统

| 子系统 | 要点 |
|--------|------|
| **文档模型** | 图层树、图层类型（像素 / 调整 / 文字 / 形状 / 组 / 智能对象）、蒙版、剪贴关系、混合模式枚举（严格对齐 PS 顺序） |
| **历史栈** | 撤销 / 重做；大操作走「引用 + 差异」而非整体快照 |
| **选区系统** | 位图蒙版（灰度）+ 矢量路径并存；蚂蚁线渲染 |
| **画笔引擎** | GPU 绘制、笔刷间距、压感（数位板，P2）、稳定器平滑 |
| **文字系统** | 编辑态用 DOM 覆盖层（contenteditable）保证输入体验，提交后按 Skia Paragraph 光栅化 |
| **文件 IO** | PNG/JPEG/WebP 走 sharp；HEIC/RAW/SVG/TIFF 走 WASM 解码；PSD 以 ag-psd 为底座 + 自研补齐 |
| **色彩管理** | lcms2（或用 sharp 内置）做 ICC 转换 |
| **工程格式** | `manifest.json` + `layers/*.png`；**v1 即引入版本号 + 显式校验 + 往返测试** |

### 6.4 Electron 分层

```
main（主进程）     窗口 / 菜单 / 原生对话框 / 文件关联 / 自动更新 / 崩溃恢复
  │  contextBridge（安全 IPC，nodeIntegration = false）
preload（预加载）  仅暴露白名单 API
  │
renderer（渲染进程）React UI + WebGPU 引擎 + Worker 池
```

## 十二、风险与取舍

| 风险 | 影响 | 应对 |
|------|------|------|
| **PSD 格式极复杂** | 读写兼容度难做满 | 先做「常用子集 + 转换报告」，明确告知哪些可编辑、哪些被栅格化；以 ag-psd 为底座 + 自研补齐 |

| **范围蔓延** | 「完整版」变无底洞 | 严格按 P0–P3 分层，每个里程碑可独立交付 |
