## 4. Windows 精准触控板 —— 实现方案

### 4.1 现状与缺口

| 输入 | 当前路径 | 问题 |
|---|---|---|
| 鼠标滚轮 | `wheel`（非 ctrl）→ 平移；`ctrl+wheel` → 离散缩放 | 不区分鼠标/触控板 |
| 触控板两指滚动 | 普通 `wheel`（deltaX/deltaY）→ 平移 | 能用，但没用 `deltaMode` 识别像素级、没 `getCoalescedEvents` 处理 120Hz 高频 |
| 触控板捏合缩放 | `ctrl+wheel` → 缩放 | 不区分触控板捏合 vs 鼠标 Ctrl+滚轮；Chromium 捏合抖动未平滑 |
| 触控板双指旋转 | **无** | `pinchDelta.rotationDeg` 算了但没人消费 |
| 三指 / 四指手势 | **无**（Chromium 不转发给页面） | 必须走 Rust 原生 |
| 压力 / 接触面积 | **无** | `POINTER_TOUCH_INFO` 带 pressure/contact，未用 |

### 4.2 三条技术路径对比

| 路径 | 做法 | 成本/风险 | 跨平台 |
|---|---|---|---|
| **A. 纯 Web 层优化** | `deltaMode` 识别、`getCoalescedEvents`、捏合平滑、双指旋转、`maxTouchPoints` 区分 | 低；不需 Rust | ✅ 自动跨平台 |
| **B. Rust 原生 WM_POINTER** | subclass WebView2 HWND 拿 `POINTER_TOUCH_INFO`，多指几何经 Tauri event 发前端 | 高；Windows-only；需 `cfg(windows)` 包裹 | ❌ Windows-only |
| **C. 混合（推荐）** | A 先做满，B 作 Windows 增强 | 中 | A 跨平台 + B Windows |

### 4.3 推荐：分阶段混合（C）
- **阶段 1（必做，纯 Web）**：设备识别 + 像素级平滑平移 + 捏合缩放去抖 + 双指旋转 + 惯性。零 Rust。
- **阶段 2（Windows 增强，Rust）**：原生 `WM_POINTER` 提供三指/四指手势、原始压力。

### 4.4 阶段 1 —— Web 层设计（`src/ui/EditorShell.tsx` + `motion.ts`）
1. **设备来源识别**：`deltaMode===0` 视为触控板/现代鼠标；捏合判定 `ctrlKey && deltaMode===0`，辅以 `navigator.maxTouchPoints`；维护 `inputSourceRef`。
2. **像素级平滑平移**：普通 `wheel(deltaMode===0)` 直接累加 `deltaX/deltaY`，用 `getCoalescedEvents()` 展开高频；Windows 已处理自然滚动方向，**不要**硬编码反向，提供 `touchpadNaturalScroll` 偏好反选。
3. **捏合缩放去抖**：`ctrl+wheel` 映射为指数平滑 `scaleNext = scale * exp(-deltaY*k)`，喂 `zoomLiveRef`；间隔 > 100ms 判定手势结束固化。
4. **双指旋转**：消费 `pinchDelta.rotationDeg`，映射视图/自由变换旋转，阈值 < 0.5° 忽略。
5. **惯性**：OS 级惯性直接消费，叠加 `flickGlide` 时仅跑一次。

### 4.5 阶段 2 —— Rust 原生（新建 `src-tauri/src/touchpad.rs`，`cfg(windows)`）
- `SetWindowSubclass` 挂 WebView2 HWND；处理 `WM_POINTER*` → `GetPointerInfo` → 维护 `HashMap<pointerId, POINTER_TOUCH_INFO>`。
- 2 指算距离/角度 → emit `touchpad-pinch{scale,rotationDeg,centerX,centerY}`；3 指 `touchpad-swipe3`；4 指 `touchpad-swipe4`；压力 `touchpad-pressure`。
- 捏合消息返回 `0`（已处理）阻止 WebView2 双重消费；其余 `CallWindowProc`。
- `Cargo.toml` 加 `windows`（锁定 0.58，不顶高 MSRV 1.77）。

### 4.6 偏好与 UI
`prefs.ts` 新增（`touchpadNaturalScroll`/`touchpadPinchZoom`/`touchpadGestures`/`touchpadInertia`，默认 true）；`App.tsx` 注入；`Preferences.tsx` 加「输入/触控板」分组 + 六语言 `preferences.input.*`。

### 4.7 文件改动清单
| 文件 | 改动 |
|---|---|
| `src/ui/EditorShell.tsx` | `wheel` 加 deltaMode/coalesced/捏合去抖/双指旋转；`inputSourceRef` |
| `src/engine/motion.ts` | 可能加 `expSmooth`、手势结束检测（纯函数+测试） |
| `src/stores/prefs.ts` | 4 个触控板偏好 |
| `src/App.tsx` / `Preferences.tsx` | 注入 + UI |
| `src/i18n/*` | `preferences.input.*` |
| `src-tauri/src/touchpad.rs`（新建）/ `lib.rs` / `Cargo.toml` | 阶段 2 |
| `tests/unit/motion.test.ts` | 补触控板纯函数测试 |

### 4.8 风险 / 回退 / 验收
- **风险**：subclass 与 WebView2 手势冲突（退路：只 emit 不 swallow）；`windows` 顶高 MSRV；Tauri event 高频负担（前端 RAF 合帧）。
- **回退**：阶段 2 不稳定先只发 `touchpad-pressure`。
- **验收**：① 两指平移丝滑无阶梯；② 捏合不误触发鼠标 Ctrl+滚轮；③ 双指旋转生效；④ 三指/四指（阶段 2）；⑤ 鼠标/笔/触屏不破坏；⑥ 非 Windows 编译通过、静默降级。

## 5. 功能深度差距：与 PhotoCraft 的代码量 / 成熟度对比

> 数据据其他 AI 提供的代码量评估。注意：**行数多 ≠ 成熟**，反而可能是冗余 / 重复 / 未接线 / 占位。下一轮的核心动作是 **audit + 真值核对 + 消灭假功能**，而非堆代码。

### 5.1 对比表

| 能力 | Strata 代码量 | PhotoCraft 代码量 | 成熟度定性（据评估） |
|---|---|---|---|
| GPU 管线 | 13,815 行 | ~1,500 行 | 我们行数多，但含 WGSL/TS 冗余与未接线部分；质量≠数量，待核 |
| 滤镜算法 | 82,531 行 | ~20,000 行 | 我们滤镜数量多（FILTER_DEFS 73+），但单滤镜深度/边缘处理待逐条核对 |
| PSD 读写 | 23,185 行 | ~2,000 行 | **PhotoCraft 更成熟**（久经考验、边界全）；我们刚修读写对称 |
| RAW 解码 | 17,011 行 | ~10,000 行 | **PhotoCraft 更成熟**；Strata 在追（已补 Clarity/Texture 真曲线） |

### 5.2 怎么追（统一动作）
1. **代码量 audit**：用 `cloc`/脚本统计各模块真实有效代码（排除测试/生成物/注释），定位「虚高」来源（例如滤镜 8 万行是否含大量重复 kernel 变体、未接线分支）。
2. **逐能力真值核对（零假功能铁律落地）**：
   - **PSD**：用真实 `.psd` 文件做 `encode→decode` 往返，核对组/文字/蒙版/调整层参数/组展开；逐项对照 PhotoCraft 常见边界（图层效果、路径、专色）。
   - **RAW**：更多格式（CR3/ARW/NEF/ORF/RAF）真实显影验证；Clarity/Texture 真曲线回归；CR3 预览明确标记。
   - **滤镜**：73 个滤镜逐个核对是否真出正确结果（不是占位 kernel），重点查高频用的模糊/锐化/USM/液化。
   - **GPU 混合**：27 种混合 CPU/GPU 像素对拍（本轮已做 62 条，扩到全参数边界）。
3. **消灭假功能**：任何 stub/占位/静默降级/假装成功 → 做真，或明确报错/标记（不假装）。
4. **成熟度对齐清单**：输出一张「PhotoCraft 有而我们没真做 / 我们做了但质量待追」的表，按收益排序逐条消项。

## 6. 跨平台：Mac / Linux（本轮修完后启动）

### 6.1 现状与硬约束
- **无本地测试环境**：用户**没有 Mac 和 Linux 机器**；手机是 Linux 但装不了 Tauri 大型 Rust 项目。
- **结论：这两个平台只能「一次成功」**——代码写对就过，没有迭代调试机会。必须把风险压到最低。

### 6.2 缓解策略（让「一次成功」可达成）
1. **CI 多平台构建（最关键保险）**：GitHub Actions 用 `ubuntu` runner 构建 Linux（deb/rpm/AppImage），用 `macos` runner 构建 Mac（.app/.dmg）。即使不能跑 UI 测试，**编译 + 打包能过**就能拦截低级错误（类型、链接、资源缺失）。
2. **条件编译严格**：平台特定 Rust 代码用 `#[cfg(target_os="macos"/"linux")]` 包裹；窗口/打包配置在 `tauri.conf.json` 的 `bundle` + 各平台 `targets`。
3. **统一抽象、平台分流**：输入（触控板/手势）、窗口效果（Acrylic/ Vibrancy/ 无）、字体回退、路径分隔符等做成平台适配层，默认走安全路径。

### 6.3 Mac 特定
- **标题栏融合**：`tauri.conf.json` 的 macOS 配置用 `titleBarStyle: "Overlay"` 或 `transparent + decorations:false` + 自定义 toolbar，把导航栏/工具栏上移到系统栏区域，融入系统 traffic lights（红绿灯）。这正是用户说的「把导航栏移到顶上 Mac 系统的那个导航栏」。
- 菜单：Mac 的应用菜单在屏幕顶部，需把 `menuCatalog` 的顶级菜单映射为 macOS 原生菜单栏（或保留应用内菜单，仅融合标题栏）。
- 签名 / notarization：打包需 Apple 开发者证书，CI 里配 `APPLE_* ` 密钥；无证书则本地双击可能被 Gatekeeper 拦（属发布流程，不影响一次成功构建）。

### 6.4 Linux 特定
- **WebViewGTK 差异**：`backdrop-filter` 在 WebKitGTK 可能不支持或不稳 → 玻璃观感提供**降级**（不透明 + 阴影），不要依赖它出效果（与 Windows 不同）。
- 运行时依赖：`webkit2gtk-4.1`、gtk 等，CI 与发布包需带或声明；AppImage 可打包依赖。
- 字体：Linux 缺微软雅黑，走 `UI_FONT_STACKS` 的 Noto/思源回退；确认中文不乱码。
- `transparent` 窗口在 X11/Wayland 行为不同 → 窗口磨砂（Acrylic 等价物）在 Linux 可能不可得，降级为普通磨砂或不透明。

### 6.5 文件改动清单（预估）
| 文件 | 改动 |
|---|---|
| `src-tauri/tauri.conf.json` | 各平台 `bundle`/`targets`、macOS `titleBarStyle` |
| `src-tauri/build.rs` / `src-tauri/src/lib.rs` | 平台特定命令 `#[cfg(...)]` |
| `src/App.tsx` / `personal.css` | 平台 dataset（`data-os`）+ 玻璃降级 |
| `src/ui/EditorShell.tsx` | 手势/输入平台适配（Linux 无精准触控板原生，走 Web 层） |
| `.github/workflows/*.yml`（新建） | 多平台 CI 构建 |
| `docs/平台适配清单.md`（新建） | 每条平台差异与应对 |

### 6.6 风险 / 验收
- **风险**：三套渲染引擎差异（WebView2/WKWebView/WebKitGTK）尤其 backdrop-filter/字体/手势；无法肉眼验证；Mac 签名。
- **验收**：CI 三平台构建全绿；交付后用户在真机点开，出问题再修（尽量靠 CI + 严格静态检查前置拦截）。

## 7. MCP server 补全

### 7.1 现状（已调研 `mcp/`）
