# 16bit 管线架构决策（2026-11-27）

> 这是「死亡之愿」批次 P1 的决策记录。结论先行：**走双轨制**——IO 层真 16bit、
> 编辑层 8bit、来源位深如实标记（`bitsPerChannel`），导出环节提供 TIFF 16bit
> 真通路。不做假的「16bit 模式」，也不在这一轮把整条管线换成 Float32。

## 1. 现状与问题

- 渲染管线钉死在 8bit RGBA（`ImageData` / `Uint8ClampedArray`）：滤镜、混合、
  变换、导出几百处都建立在这个表示上。
- `StrataDoc.bitsPerChannel` 字段早已存在，但**是死标记**：只有图像 > 模式菜单
  在写它，打开管线不读源位深、导出不用、工程序列化不存、PSD 桥接写死 8。
- 16bit TIFF 打开时「取高字节」截断（等于 ÷256，暗部整体偏亮近 1/255）；
  16bit PNG 被浏览器解码器静默压成 8bit——数据没了但用户不知道。

## 2. 方案对比

| 方案 | 描述 | 代价 | 结论 |
|---|---|---|---|
| A 双轨制（本轮） | IO 真 16bit 进出；编辑层 8bit；位深标记贯穿模型/工程/导出 | 小，可增量 | **采用** |
| B 全管线 Float32 | 像 Krita/Photoshop 那样全通道高精度合成 | 数百处改写 + 性能翻倍，无法增量交付 | 不做，但接口按可升级设计 |
| C 全 8bit + 口径 | 承认 8bit、砍掉 16bit 宣传 | 与专业站队目标冲突 | 不做 |

## 3. 本轮落地（全部真实可验证）

1. **源位深探测** `core/bitDepth.ts`（纯函数 + 5 测）：PNG IHDR 直接读 bit depth；
   TIFF 轻解析 BitsPerSample（tag 258，含内联/外部两种布局）。
2. **打开管线** `openFile.ts`：TIFF/PNG 探测源位深，`doc.bitsPerChannel = 16`
   如实标记；不再静默。
3. **TIFF 解码修正** `engine/tiff.ts`：16→8 改为 `round(v·255/65535)`（÷257 精确舍入），
   旧的取高字节（÷256）在暗部有系统性偏差；解码结果带 `depth` 字段。真值测试用
   手构 16bit 灰度 TIFF 钉死（选了 32768→128、255→1 等「取高字节会错」的样本防恒真）。
4. **TIFF 16bit 写侧** `encodeTiff16()`：无压缩 RGBA16（小端 II），编码器与解码器
   同文件互验；导出对话框新增「TIFF 16bit」格式。
5. **导出联动**：`doc.bitsPerChannel = 16` 的文档默认选 TIFF 16bit；用户改选 8bit
   格式时明确警告「位深会掉回 8」，不做静默降级。
6. **工程往返**：`.strata` v6 起携带 `bitsPerChannel`，旧工程按 8。

## 4. 明确不做的（防止做成假 16bit）

- 不把 8bit 编辑层伪装成「16bit 模式」：菜单里的 16 位/通道勾选仍是标记语义，
  但现在这个标记有真实来源（打开管线）和真实出口（TIFF16 导出 + 工程往返）。
- 不做 16bit 滤镜/混合计算：编辑层是 8bit，所有调整在 8bit 上算。
  什么时候升级到 B 方案，取决于用户反馈里「16bit 编辑精度」诉求的强度。
- 32bit float：EXR 读侧已有（`strata_exr_read`），编辑层同样 8bit；本轮不动。

## 5. 下一步（按需求强度排）

1. CMYK：TIFF/PSD 的 CMYK 正确读入 → ICC 转 RGB 显示 → 保留原始数据供导出。
2. PSD 16bit 读侧如实标记（当前 PSD 桥接写死 8，见 psd.ts）。
3. 若「16bit 编辑精度」诉求成立：编辑层缓冲换 Uint16/Float32 的迁移计划
   （先滤镜层试点，因为滤镜已经全部走「Raster + 纯函数」的可替换形态）。
